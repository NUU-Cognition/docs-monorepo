---
title: "Agent Sessions"
---

Agent sessions are one of Flint's most important current features because they make agent work durable and inspectable.

Flint is not only a place to store notes about agent work. It is an environment where agents can execute shard-based cognitive programs, and Orbh sessions are the state model that tracks those executions over time.

## Where Sessions Live

Current session spools are Orb-backed. In a local Flint they live under:

```text
.orb/spaces/local/spools/
```

These files are local session state, not published workspace content. The Flint-managed `.gitignore` excludes the local Orb space, while Orbh can also promote or move spools between spaces when a synced space is configured.

## What a Session Tracks

The implemented session model includes:

- stable session id
- space id
- work state
- runtime name
- runtime profile
- launch prompt
- working directory
- mode (`interactive`, `headless`, or `subagent`)
- optional parent session id
- optional title and description
- one or more runs
- request/response records
- interface key/value state
- tracked artifact paths
- result text

The lifecycle field used by Orbh work queues is `workState`. Current work states include:

- `working`
- `needs-input`
- `finished`
- `abandoned`

Each run records a concrete harness invocation, including the native runtime session id and transcript path when the runtime provides them.

## Main Commands

Launch a headless session:

```bash
flint orbh launch codex "Review the codebase and update notes."
```

Launch and wait for a request-style session:

```bash
flint orbh request -q codex/55xh "Review the codebase and update notes."
```

Inspect active or historical sessions:

```bash
flint orbh list --print
flint orbh active --json
flint orbh inspect <id>
flint orbh watch <id>
flint orbh result <id>
flint orbh wait <id>
```

Session lifecycle and control commands include:

```bash
flint orbh resume <id> "Continue working"
flint orbh kill <id>
flint orbh close <id>
flint orbh park <id>
flint orbh discard <id>
```

Agent-facing session actions live under `flint orbh session`. When `ORBH_SESSION_ID` is set inside a harness, the id can be omitted for self-targeting actions:

```bash
flint orbh session register "Short title" "What this session is doing"
flint orbh session set phase reading-code
flint orbh session get phase
flint orbh session return "Full result as markdown"
flint orbh session note "Short operational note"
```

## Human-Agent Exchange

The Orbh interface supports structured communication between a session and its operator:

```bash
flint orbh session ask "Question?"
flint orbh respond <id> "Answer"
flint orbh requests <id>
flint orbh request <id> "Deferred question?"
```

`ask` waits for a reply before continuing. `request` can also post a deferred question to an existing session; when the session is resumed after a response, the resume prompt tells the agent to inspect `flint orbh requests <id>`.

This matters because long-running cognitive work often needs checkpoints, clarifications, or human decisions without throwing away session state.

## Runs and Resume

One session can contain multiple runs. Flint supports:

- a brand-new session
- continuation of a prior session
- resume of an existing session with another run

That is why the model tracks both session-level state and run-level state. The session is the durable container. Each run is a concrete execution attempt inside that container.

## Session Tracking in Artifacts

Agents track their involvement in Mesh artifacts through the `orbh-sessions` frontmatter field. This is a unified field — all agent runtimes (Claude Code, Codex, etc.) write to the same field.

```yaml
orbh-sessions:
  - "[session-uuid-1](/flint/session-uuid-1)"
  - "[session-uuid-2](/flint/session-uuid-2)"
```

Each entry is the Orbh session ID wrapped in wikilink syntax. The Orbh session maps to native runtime sessions via its runs model. When an agent creates or substantively edits an artifact, it appends its session ID to this list.

Previously, session tracking used per-runtime fields (`claude-sessions`, `codex-sessions`). These have been consolidated into the single `orbh-sessions` field. A migration handles converting existing files.

Agents not launched via `flint orbh` should still write to `orbh-sessions` using whatever stable session identifier they have available, or skip session tracking if no identifier exists.

## Sessions and the Rest of Flint

Agent sessions connect Flint's environment model together:

- shards define the cognitive programs
- the agent session records the execution state
- Mesh stores the durable notes and artifacts produced by that work

Taken together, this is what makes Flint more than a prompt wrapper. It provides memory, continuity, and a workspace-native record of what the agent actually did.
