---
title: "The Models Framework"
---

Flint is built around a practical idea: a workspace is useful when it helps people and agents build workable models of reality.

A model is any representation that helps a mind understand or act. A note is a model. A task is a model. A transcript, a guide, a plan, and a type definition are all models too. None of them is reality itself. They are structured ways of pointing at reality, interpreting it, and making it useful inside a workspace.

This page explains the conceptual stance behind Flint's artifact system.

## The Starting Point

Flint starts from two simple assumptions:

- there is a shared reality outside the workspace
- every mind works through models of that reality

That distinction matters because Flint does not treat its file types as natural categories. A `(Task)` is not a kind of thing that exists in the world. It is a useful structure for representing work that should happen. A `(Record)` is not a separate metaphysical class. It is a way to preserve a captured event or observation with less interpretation than a guide or plan.

The system is designed for usefulness, not purity. A structure earns its place when it helps someone retrieve, verify, compare, compose, or act.

## Meaning Depends on Context

A note only makes sense inside an interpretation context. Flint calls that context an Information Environment.

An Information Environment can be:

- a person reading with their current background knowledge
- an agent session with certain files loaded into context
- a shard with its init file, templates, and knowledge available
- a future maintainer opening a document months later

The same markdown file can mean different things in different contexts. A terse task note may be obvious to the person who wrote it and confusing to an agent that has not loaded the relevant shard. A record may be strong evidence that something was said, but weak evidence that what was said is true.

Good Flint documents make their expected context legible. They link to related notes, name source material, use frontmatter consistently, and avoid assuming that the next reader has the same working memory as the original author.

## Types Are Compositions, Not Categories

Flint types are named patterns of useful traits.

For example:

- a task combines a future-oriented outcome, a commitment to do work, and lifecycle states like `todo`, `in-progress`, and `done`
- a record combines captured content, a past event, and a strong expectation that it should not be rewritten casually
- a concept combines a reusable idea, dense links to neighboring ideas, and an evergreen lifecycle

This is the main design move: do not ask "what bucket does this belong in?" Ask "what traits does this need so the workspace can operate on it?"

That is why Flint can add, split, merge, or retire types over time. Types are tools. They are not claims about how the world is carved up.

## Capture and Synthesis Form a Spectrum

Some workspace material is close to capture. Other material is heavily synthesized.

At the capture end are things like logs, transcripts, sensor readings, screenshots, and copied source material. The value is that they preserve something that happened or existed with minimal added interpretation.

At the synthesis end are things like explanations, plans, policies, design notes, and concept documents. The value is that a mind has selected, interpreted, reduced, and organized the material into something more useful.

Most artifacts sit somewhere between those ends. Meeting notes may include direct quotes, summarized decisions, and the author's interpretation. A research note may contain copied source excerpts and a new argument built on top of them.

Flint works best when that difference stays visible. Captured material is useful for grounding. Synthesized material is useful for action and understanding. Mixing them is normal, but the reader should be able to tell which is which.

## Records Say What Was Captured

A record-like artifact proves that a capture event happened. It does not automatically prove every claim inside the captured content.

For example, a transcript can support the claim "this person said these words in this meeting." It does not, by itself, support the claim "the thing they said is true." That second claim needs its own grounding.

This distinction is important for agent work. When accuracy matters, agents should trace synthesized claims back toward records, source files, or other grounding material instead of treating a polished note as direct evidence.

## Traits Stay Orthogonal

Flint treats many document properties as independent traits rather than a single hierarchy.

Useful traits include:

- time orientation: past, present, or future
- confidence: directly described or inferred under uncertainty
- scale: a whole system, a feature, a file, or a single event
- resolution: a broad summary or a detailed account
- aliveness: active, stable, retired, or superseded
- grounding: source-backed, event-backed, assumed, or ungrounded
- commitment: draft, working, endorsed, or canonical

These traits can be combined. A document can be future-oriented and uncertain. A record can be detailed but narrow in scale. A guide can be stable but still not canonical.

The point is not to fill out every possible field. The point is to add structure only where it creates a real affordance.

## Structure Is Progressive

Not every idea needs a full type, template, lifecycle, and metadata scheme on day one.

Flint supports a gradual path:

1. start with ordinary prose
2. add links when relationships matter
3. add tags when discovery or grouping matters
4. add frontmatter when automation needs stable fields
5. add a template or type when the pattern repeats and deserves operations

This keeps the workspace from becoming heavy too early. A lightly structured note is not a failure. It is often the right form until repeated use proves that more structure would help.

## The Practical Rule

When shaping a Flint artifact, ask:

- what is this document trying to help a person or agent do?
- what context does a reader need to interpret it correctly?
- how close is it to captured source material versus authored synthesis?
- which traits should be explicit because tools or readers will use them?
- is there already a type that gives this pattern the right affordances?

If the answers are clear, the document probably belongs in the workspace. If the structure does not help anyone act, retrieve, verify, or compose, keep it simpler.
