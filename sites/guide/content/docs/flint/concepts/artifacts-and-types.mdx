---
title: "Artifacts and Types"
---

Artifacts are the concrete markdown files that make a Flint workspace durable. The models framework explains why structure exists; artifacts and types explain how that structure becomes something people and agents can use.

An artifact is not just a file on disk. It is a document with a title, metadata, body content, links, and conventions that tell Flint how to work with it.

## From Model to Artifact

Every artifact is a model with enough structure to be useful in a workspace.

That structure usually comes from a few visible surfaces:

- the filename
- YAML frontmatter
- tags
- links
- the markdown body
- an optional template
- an optional lifecycle

Different artifacts use different amounts of structure. A quick note may only need an `id` and a tag. A task may need status, priority, parent links, and a lifecycle. A documentation page may need authors, source references, and a last verified date.

The guiding rule is simple: add structure when it enables a reader, agent, or command to do something better.

## Names Carry Shape

Flint filenames communicate how a file should be read.

Typed artifacts usually follow this pattern:

```text
(Type) NNN Name.md
```

Examples include:

```text
(Task) 042 Implement source refresh.md
(Plan) 007 Documentation cleanup.md
```

The type prefix tells the reader which pattern the artifact follows. The number gives the type a stable local sequence. The name describes the specific artifact.

Some workspace files use a type prefix without a number:

```text
(System) Flint Init.md
(Dashboard) Backlog.md
```

Untyped notes are simpler:

```text
Context windows limit agent memory.md
```

That does not make them less important. It only means the note does not need a typed operational pattern yet.

## Frontmatter Is the Machine-Readable Surface

YAML frontmatter gives tools and agents a stable way to inspect the artifact without parsing the whole document body.

Most artifacts include:

```yaml
id: a stable UUID
tags:
  - "#doc/concept"
```

Other common fields include:

```yaml
status: in-progress
template: "[tmp-proj-task-v0.1](/flint/tmp-proj-task-v0-1)"
authors:
  - "[@Nathan](/flint/nathan)"
orbh-sessions:
  - "[session-id](/flint/session-id)"
last-verified: 2026-07-07
```

The `id` is the permanent identity. The title can change, but the ID should not.

Tags support discovery and grouping. Authors record the person responsible for the artifact. Orbh session links show which agent sessions created or changed it. Template links explain which structure the artifact was generated from.

Frontmatter should stay purposeful. A field that no person, agent, or command reads is probably not worth adding.

## Tags Express Useful Traits

Tags are lightweight signals. They do not need to express everything about an artifact.

Common Flint tag patterns include:

```yaml
tags:
  - "#note/concept"
  - "#note/record"
  - "#proj/task"
```

A tag can identify a subtype, a shard-owned pattern, or a state that should be easy to query. Tags work best when they are cheap to apply and useful to search.

Tags are not a full ontology. They are handles for discovery and operations.

## Templates Make Patterns Repeatable

A template tells an agent how to create or edit a recurring kind of artifact.

Templates define things like:

- where the file should live
- how the filename should be shaped
- which frontmatter fields belong
- which sections the body should contain
- what lifecycle values are valid

Agents should treat templates as instructions, not as text to copy blindly. A good generated artifact follows the template's intent while replacing placeholders with real content.

Templates are useful when repeated artifacts should be consistent. They are unnecessary when a one-off note only needs ordinary prose.

## Types Package Affordances

A type is a named composition that gives a recurring artifact pattern a set of affordances.

For example, a task type can support:

- numbered task filenames
- status transitions
- project or increment links
- backlog dashboards
- archive behavior

A record type can support:

- stable capture notes
- source-oriented titles
- fewer lifecycle transitions
- stronger expectations around preserving original content

The important question is not "what category is this?" The important question is "what can Flint do with this structure?"

If a type does not improve creation, retrieval, validation, reporting, review, or automation, it probably should not exist yet.

## Type Definitions Live in Metadata

Shards can install type definition files into:

```text
Mesh/Metadata/Types/
```

Those files describe the type for humans and agents. They usually document:

- the tag associated with the type
- the naming convention
- the storage location
- archive behavior
- lifecycle states
- related templates

The type definition is documentation for the pattern. It is not the artifact itself.

Type definitions are shard-qualified so different shards can define similarly named patterns without colliding.

## Types and Folders Are Separate

A type does not automatically imply a storage folder.

One shard may define a type and also create folders such as:

```text
Mesh/Types/Tasks/
Mesh/Archive/Tasks/
```

Another shard may define a type that has no dedicated artifact folder at all.

This separation keeps Flint explicit. Type definitions describe meaning and behavior. Folder declarations describe where files are stored. The relationship between them is intentional rather than automatic.

## Lifecycles Are Part of the Model

Some artifacts have lifecycle states because their role changes over time.

A task might move through:

```text
todo -> in-progress -> review -> done
```

A document might be:

```text
draft -> working -> verified -> retired
```

A record may have little or no lifecycle because its value comes from preserving a capture.

Lifecycle fields are not decoration. They help dashboards, agents, and humans decide what action is appropriate next.

## When to Add More Structure

Use the lightest structure that serves the work.

Add a tag when you need grouping or discovery. Add frontmatter when a field should be read by tools or queried later. Add a template when a pattern repeats. Add a type when the pattern deserves named operations and lifecycle rules.

This is how the models framework becomes practical: Flint starts with plain markdown, then adds just enough structure for the workspace to think and act reliably.
